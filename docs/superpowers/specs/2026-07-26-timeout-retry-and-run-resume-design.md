# 模型超时自动重试与运行断点恢复设计

## 1. 目标

解决模型请求偶发超过 120 秒后整次测验开发任务终止、且程序重启后无法继续的问题。

修改后的系统应当满足：

1. 模型请求超时时进行有限自动重试；
2. 每个工作流状态更新后持久化当前运行状态；
3. 程序重启后能够从最后保存的业务状态继续；
4. 已确认并提交、或已进入候选题库的题目不得重复生成；
5. 仍然保留超时上限，避免请求无限挂起；
6. 构念建模使用稳定的 `source_id` 关联检索证据，引用标题由程序回填；
7. 不改变现有题目生成、审查、题库冻结和后续心理测量流程的业务规则。

## 2. 已确认的现状

- `sjt_system.execute._ainvoke_model` 使用统一的 120 秒外层超时；
- 模型超时不会自动重试；
- `execute_node` 把所有异常转换为 `status="failed"`，随后工作流结束；
- LangGraph 使用 `InMemorySaver`，检查点只存在于当前 Python 进程；
- CLI 每次启动都会创建新的 `run_id` 和初始状态；
- 当前环境没有安装 LangGraph SQLite checkpointer 扩展。

因此，单纯增加超时时间不能解决进度丢失；仅替换 LangGraph checkpointer 又会引入新的依赖和迁移范围。

## 3. 方案比较

### 方案 A：仅增加模型重试

优点是改动小。缺点是重试耗尽或程序退出后仍然无法恢复，不满足用户的核心需求。

### 方案 B：引入 LangGraph SQLite checkpointer

优点是由 LangGraph 管理持久化检查点。缺点是当前项目未安装相应扩展，需要新增依赖；还需要处理已有内存检查点、CLI 运行选择和失败状态恢复语义，改动面较大。

### 方案 C：模型有限重试＋应用级 JSON 状态快照

不新增第三方依赖，在现有 CLI 流程外围保存完整 `PSJTState`。重启时读取快照、恢复 `status`，再从 LangGraph 的 `START -> router` 重新进入；Router 根据已提交的业务状态选择下一项未完成任务。

选择方案 C。它满足当前需求，沿用项目已有的原子 JSON 写入模式，并避免把运行恢复绑定到某个 LangGraph checkpointer 实现。

## 4. 构念建模来源规范化

### 4.1 问题

当前构念建模同时返回 `source_id` 和 `citation_label`。虽然
`source_id` 已能唯一关联检索证据，程序仍要求模型逐字复制长标题。
模型只要改变标题中的标点、空格、大小写或翻译方式，整次运行就会失败。

### 4.2 规范化规则

`source_id` 是唯一可信的来源关联键：

1. `source_id` 不在当前 `theory_evidence` 中时拒绝候选结果；
2. `source_id` 合法时，程序忽略模型提供的 `citation_label`；
3. 程序从对应证据的 `title` 回填标准 `citation_label`；
4. 规范化后的结果继续通过现有严格校验后才能写入 State。

不采用模糊标题匹配，因为相似标题可能属于不同文献，会削弱来源真实性。

### 4.3 无效来源修复

如果模型返回不存在的 `source_id`，把错误原因和合法来源 ID 列表反馈给
构念建模 Agent，使用现有有界结构修复模式重新生成。修复次数与其他结构化
输出修复保持一致；耗尽后保存失败断点。

## 5. 自动重试设计

### 5.1 配置

新增环境变量：

- `MODEL_REQUEST_MAX_ATTEMPTS`：单个模型请求的最大总尝试次数，默认 `2`；
- 合法范围为 `1` 至 `5`；
- 现有 `MODEL_REQUEST_TIMEOUT_SECONDS` 继续表示每次尝试的超时时间。

默认行为是首次请求超时后自动再尝试一次。设置为 `1` 可恢复当前“不重试”的行为。

### 5.2 重试范围

第一版只自动重试已明确观察到的 `TimeoutError`。结构化输出校验失败继续使用现有的结构修复机制，不与网络超时重试混合计数。

模型路由请求和各专业 Agent 请求采用同一最大尝试次数，避免 Router 超时仍然直接终止。

### 5.3 退避与进度信息

每次超时且仍有剩余尝试时：

1. 发出 `request_retry` 进度事件；
2. 显示任务名称、下一次尝试序号和最大尝试次数；
3. 等待短暂退避后重试。

最终尝试仍超时时，保留现有 `request_timeout` 事件和清晰的失败信息。重试不会无限进行。

## 6. 持久化快照设计

### 6.1 存储位置

每个运行保存为：

`outputs/run_checkpoints/<run_id>.json`

文件使用 UTF-8，并通过“写临时文件后原子替换”的方式保存，避免程序在写入途中退出造成半个 JSON 文件。

### 6.2 快照格式

快照顶层包含：

- `schema_version`：当前为 `1`；
- `run_id`；
- `saved_at`；
- `is_terminal`；
- `state`：完整的 `PSJTState`。

加载时必须验证顶层结构、版本、`run_id` 与状态中的 `run_id` 一致，并拒绝损坏或版本不支持的文件。

### 6.3 保存时机

`run_with_trace` 每收到一个有效 LangGraph 状态更新并合并到 `result` 后立即保存。

这样可保存：

- 已确认的需求、构念模型和蓝图；
- 已确认并提交的题目生成或审查结果；
- 已完成的题库审核、模拟、分析和组卷结果；
- 最终失败状态及失败前已提交的全部业务状态。

在 `completed` 或用户主动 `stopped` 时仍保存最终快照，但标记为终态，不在默认的“可恢复任务”列表中显示。

## 7. 恢复流程

### 7.1 启动选择

CLI 启动时扫描非终态快照。存在可恢复任务时，显示最近一次运行的：

- `run_id`；
- 保存时间；
- 当前阶段；
- 已通过题目数；
- 最近失败原因。

用户可以选择：

1. 继续最近一次运行；
2. 开始新运行。

第一版只提供“继续最近一次”，不实现多运行管理界面。

### 7.2 状态规范化

恢复前创建状态副本，并进行最小修复：

- 把 `status="failed"` 改为 `status="running"`；
- 保留 `errors` 和 `execution_history` 作为审计记录；
- 不删除题目、题库、进度计数或已提交的分析结果；
- 清空 `pending_action`、`pending_state_update`、`pending_summary`、
  `pending_state_changes`、`pending_interaction`、`user_decision` 和
  `user_feedback`，防止把未提交的候选结果当成已批准结果；
- 保留 `run_id`。

恢复状态作为新的图输入进入 Router。Router 根据业务状态重新选择未完成动作。例如题库尚未审核时会再次选择 `audit_item_bank`，而已经进入候选题库的题目不会重新生成。

### 7.3 恢复边界

快照只保证“步骤级”恢复，不尝试恢复正在传输中的单个 HTTP 请求。超时发生时，该次请求没有已提交结果，因此恢复后重新执行该动作是正确行为。

在本功能上线前已经失败且没有快照的旧运行无法恢复。

## 8. 组件与文件职责

### `sjt_system/agent/API.py`

解析并校验模型请求最大尝试次数配置。

### `sjt_system/execute.py`

对专业 Agent 的单次模型调用执行有限超时重试，并发送重试进度事件；
对构念建模候选结果执行来源规范化和有界结构修复。

### `sjt_system/theory_search.py`

根据合法 `source_id` 回填标准 `citation_label`，并继续执行严格来源校验。

### `sjt_system/graph.py`

让 Router 模型调用使用相同的有限重试策略，保持失败记录语义不变。

### `sjt_system/run_checkpoint.py`

新增独立模块，负责：

- 原子保存快照；
- 加载和验证快照；
- 查找最近的可恢复运行；
- 将失败状态规范化为可继续运行状态。

该模块不调用模型，也不包含 CLI 输入输出。

### `app.py`

负责：

- 展示重试进度；
- 在每个状态更新后保存快照；
- 启动时询问继续运行或开始新运行；
- 把恢复状态传给 `run_with_trace`。

## 9. 错误处理

- 快照目录不存在时自动创建；
- 单个快照损坏时给出明确提示，不把损坏状态送入工作流；
- 快照保存失败时立即报告，因为继续运行却不再持久化会制造虚假的可恢复承诺；
- 重试只捕获超时，不吞掉结构校验、业务校验和编程错误；
- 构念来源标题差异由程序规范化，不消耗额外模型请求；
- 不存在的 `source_id` 才触发构念输出结构修复；
- 重试耗尽后仍按现有方式将运行标记为失败，并保存可恢复快照。

## 10. 测试策略

采用测试先行：

1. 来源规范化测试：合法 `source_id` 自动回填检索标题；
2. 来源拒绝测试：不存在的 `source_id` 不得通过；
3. 构念修复测试：无效来源首次失败、反馈后成功及修复耗尽；
4. 配置解析测试：默认值、覆盖值、非法值；
5. 模型重试测试：首次超时后成功、重试耗尽、非超时异常不重试；
6. 进度事件测试：重试事件包含正确任务名和尝试次数；
7. 快照测试：原子写入、往返加载、损坏文件和版本不支持；
8. 恢复规范化测试：只重置瞬时控制字段，保留题库和历史；
9. CLI 测试：检测到快照时可选择继续或新建；
10. 集成回归测试：题库审核超时、保存失败状态、恢复后再次审核，已通过题目数量和标识保持不变。

完成后运行相关定向测试与完整测试套件。

## 11. 非目标

本次不实现：

- 图形化任务管理界面；
- 多台机器共享检查点；
- 对任意网络错误进行无差别重试；
- 恢复本功能上线前未保存的旧运行；
- 修改题目质量标准或审核判定规则；
- 更换当前模型或第三方网关。
